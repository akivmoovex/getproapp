REGISTRATION_ENTRY=The register-church application repository creates the registration application; `provisionRegisteredBlessBoardChurch(db, input, options)` locks it, provisions the organization/church/branch, resolves the administrator, creates or reuses the BlessBoard administrator, assigns church roles, and commits through `withProvisioningTransaction`.
LEGACY_USER_CREATION=At `provisionRegisteredBlessBoardChurch.js` stage `create_administrator_user`, the fresh path calls `createBlessBoardUser`. Existing-user and invitation paths resolve/reuse a `blessboard.users` row through `resolveBlessBoardRegistrationAdministrator`.
ROLE_ASSIGNMENT_ROOT_CAUSE=The workflow invokes `assignBlessBoardRole` for `church_hq_admin` and `branch_admin`, but those are legacy BlessBoard role records. The fresh persisted result observed in Phase 4J.5 had no verified active `blessboard.user_roles` row for the returned administrator, and in all cases no V5 platform identity/product link was created. The first defect is therefore the missing V5 principal bridge; the role-row absence must be covered by a regression assertion and diagnosed inside the role-assignment return path rather than patched with SQL.
V5_LOGIN_CONTRACT=The V5 session layer accepts product-compatible principals. BlessBoard uses a `blessboard_user`/linked principal; ActiveClinic uses a `platform_identity` principal. A usable V5 BlessBoard login must resolve an active BlessBoard user, deployment-compatible product access, organization/church membership, and effective website permissions. `platform.identities` alone is not authorization.
EXISTING_IDENTITY_BRIDGE=No existing automatic BlessBoard bridge was found. `identityProductProfileService` can link a platform identity to a `blessboard_user` profile, but linking explicitly does not grant organization/product access. Registration identity resolution currently operates on BlessBoard users and does not call platform identity creation, credential, product-profile linking, or membership services.
MISSING_RELATIONSHIPS=For a V5-compatible registration result: (1) active platform identity and credential linkage if the selected V5 path requires it; (2) BlessBoard product/profile link with profile type `blessboard_user`; (3) organization/product membership; (4) church membership/active HQ and branch roles; (5) website editor/publisher permission closure. The bridge must verify each relationship through repository/service APIs.
TRANSACTION_STRATEGY=Extend the existing registration provisioning transaction or invoke one nested service with `manageTransaction:false`; perform identity bridge, profile link, membership, role assignment, and permission verification before commit. Any failure must throw the existing orchestrator error so the whole registration transaction rolls back. Never create a partial identity or manually repair authorization after commit.
IDEMPOTENCY_STRATEGY=Reuse the existing contact-resolution decision first. Lock normalized email/phone contacts; if an existing platform identity is compatible, reuse it only after password/ownership checks. If no identity exists, create exactly one identity and credential. Use idempotent profile/membership/role service calls, validate same-organization retry as already provisioned, reject email/phone split conflicts, reject suspended principals, and preserve invitation semantics (invitation does not accept a self-service password).
EXISTING_USER_COMPATIBILITY=Keep the legacy `blessboard.users` row and password hash unchanged for legacy routes. For existing compatible users, add/link the V5 representation without overwriting credentials. For an existing platform identity belonging to another church or conflicting contact, return the existing identity-conflict result. Do not silently merge accounts.
SCHEMA_MIGRATION_REQUIRED=Prefer none. Existing platform identities, product profiles, organization products, BlessBoard users/roles/permissions, and membership structures are present. Confirm exact repository APIs and constraints in implementation tests; add schema only if a service proves a missing relationship cannot be represented.
FILES_TO_CHANGE=Minimal implementation candidate: `src/blessboard/services/provisionRegisteredBlessBoardChurch.js` (or a new small BlessBoard registration-to-platform bridge service); possibly `src/blessboard/services/resolveBlessBoardRegistrationAdministrator.js` only if identity resolution must return a paired platform principal. Reuse existing platform identity/credential/product-profile and BlessBoard authorization repositories. Extend existing registration identity-idempotency tests and add a focused V5 registration auth integration test. No runtime route or migration changes are required by this design.
REGRESSION_TEST_PLAN=Add tests for fresh registration creating both legacy compatibility and V5 eligibility; existing platform identity reuse; same-church retry; email/phone conflict; suspended identity rejection; HQ/branch website permissions; real V5 browser login; cross-tenant login denial; invitation flow without password overwrite; and forced failure rollback asserting no orphan platform identity, product link, membership, role, or credential. Assert exact service results and persisted relationships, not only HTTP redirects.
